Wardrik is one daemon and the `wardrik` command that runs it and asks it things. The release runs
on Linux, on x86_64 or arm64, with glibc 2.35 or later and OpenSSL 3: Ubuntu 22.04 and later, and
Debian 12 and later. Elsewhere, such as on macOS or Alpine, run the Docker image.

<Tabs>
	<TabItem label="Install script">

```sh
curl -fsSL https://github.com/wardrik-dev/wardrik/releases/latest/download/install.sh | sh
```

The script checks the release against its `SHA256SUMS`, runs it once to be sure it runs on this
machine, and installs it under `~/.local`, or under `/opt/wardrik` as root. `wardrik` goes on your
`PATH` in `~/.local/bin`, and so does `rik`, unless something else on the machine is already called
that.

`WARDRIK_VERSION=0.1.0` installs a version other than the latest, and `sh install.sh
wardrik-0.1.0-linux-x86_64.tar.gz` installs a tarball you already have.

	</TabItem>
	<TabItem label="Docker">

```sh
docker run -d --name wardrik -p 127.0.0.1:4747:4747 -p 2222:2222 \
  -v wardrik-config:/config -v wardrik:/data ghcr.io/wardrik-dev/wardrik
docker exec -it wardrik wardrik init
```

The image runs `wardrik serve` as the user `wardrik`, uid 1000. `/config` holds what you write,
`config.yaml`, `agents/` and `policies/`, and what `wardrik init` writes for you; `/data` holds the
store, the cookie, the SSH host key and the vault's key, `/data/vault_key`. Both are volumes, so a
new container on the same volumes carries on.

To edit `/config` on the host, mount a directory of yours there instead, one uid 1000 can write,
as the first user's is on most Linux machines: `-v ~/.config/wardrik:/config`. `wardrik init`
stops, and says so, where it cannot write `/config`.

The HTTP API listens on port 4747 and the TUI on 2222, on every interface of the container, so the
ports you publish decide who reaches them.

	</TabItem>
</Tabs>

## Set it up

```sh
wardrik init
```

`wardrik init` says what it finds, then asks for a model provider, offering those whose key your
shell already sets, a model, the provider's key, which it does not show as you type, and the first
agent's name. It writes `agents/assistant.md` with that model and no tools, and a `config.yaml`
whose `defaults` give that model to each agent `wardrik agent spawn` starts, offers to let your SSH
keys in for `wardrik attach`, starts the daemon, under your systemd from boot if you like, seals
the key in the vault, and asks the agent one short question. It writes no file that is there
already, so it can run again.

Without a terminal, as in a script, flags answer its questions:

```sh
wardrik init --provider anthropic --key-from-env ANTHROPIC_API_KEY --yes --no-service
```

| Flag | Answers |
| --- | --- |
| `--provider P` | the model provider, which has no default |
| `--model M` | the model, the provider's newest unless given |
| `--agent NAME` | the first agent's name, `assistant` unless given |
| `--key-from-env VAR` | the provider's key, read from `VAR`; without it, the provider's own variable, such as `ANTHROPIC_API_KEY` |
| `--yes` | yes to each yes or no: the vault's key, your SSH keys, the service |
| `--no-service` | start the daemon with `wardrik start`, not under systemd |
| `--no-ask` | ask the agent nothing |

A question with no default and no flag fails, naming the flag.

## Run it by hand

```sh
wardrik service install    # under your systemd, from boot
wardrik start              # or in the background, until you stop it
wardrik doctor             # whether what it reads will do
```

`wardrik service install` writes `wardrik.service` under `~/.config/systemd/user`, starts it, and
lets your systemd run from boot rather than from your first login.

`~/.config/wardrik/env` sets variables for every `wardrik` command and the daemon it starts, one
`NAME=value` a line, such as a key `config.yaml` names as `${NAME}`. A variable the shell sets
already wins. Keep the file readable by you alone: `chmod 600 ~/.config/wardrik/env`.

`wardrik doctor` checks the env file, `config.yaml`, the store, the vault, each MCP server and every
agent file, whether the daemon runs or not.

## Keep secrets in the vault

```sh
wardrik vault put LINEAR_TOKEN    # asks for the value, and does not show it
wardrik vault ls
```

The vault seals secrets, such as the credential an MCP server reads with `credential:
LINEAR_TOKEN`, and keeps them in the store. The first `vault put` asks to make the vault's key,
and keeps it in `~/.local/share/wardrik/vault_key`, or `/data/vault_key` in Docker, beside the
store: anyone who can read both can read the secrets. To keep them apart, set `WARDRIK_VAULT_KEY`
in the daemon's environment, or `vault.keys` in `config.yaml`, before the first `put`.

The nodes of a cluster on one machine share the key. A node on another host needs a copy of
`vault_key`, as it needs the cookie, or every node needs the same `vault.keys`.

## Upgrade

Run the install script again. It puts the new release beside the old one and points `wardrik` at
it, keeping the one before. The service runs the new release when it restarts:

```sh
systemctl --user restart wardrik
```

## Remove it

```sh
wardrik service uninstall
```

The service is stopped and its unit removed. What the daemon keeps stays in
`~/.local/share/wardrik` until you remove it.
